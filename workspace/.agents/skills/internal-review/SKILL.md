# internal-review

対象は今のスレッド（`_ops/threads/<thread-id>/`）。使うファイルは次の2つだけで、実施日時や成果物ごとに分けない。

| ファイル | 役割 | 書き方 |
| --- | --- | --- |
| `<thread-id>-REVIEW.jsonl` | 永続記録。指摘・根拠・回答・判断・修正・確認の経緯をすべて残す | 指摘の行は該当行だけ Edit、経緯の行は `>>` で追記するだけ |
| `work/review/<thread-id>-review-pending.md` | 人間が確認する未解決一覧。REVIEW.jsonl と成果物から作り直せる派生ビュー | 丸ごと作り直してよい |

無ければ最初の記録のときに作る。

## どこから始めるか

- 「レビューして」と言われた → 1 から
- 誤りの指摘を受けた・指摘に回答や指示があった・指摘に関わる修正や確認をした・保留の理由が変わった → 3 から
- 「R-001 を RULES に入れて」と指示された → 6

## 1. 記録を見ずにレビューする

REVIEW.jsonl を読む前に、成果物と一次資料（仕様書・項目定義書など、成果物の元になった資料）だけを見てレビューする。先に読むと、記録済みの観点に引きずられて新しい問題を見落とすため。読み込み済みの RULES.md は、そのまま適用する（まだ読んでいなければ先に読む）。

## 2. 記録と照合する

REVIEW.jsonl の指摘の行を読み、1 の結果と照合する。

- 解決済の指摘が再発していないか（再発なら同じ ID を開き直す）
- 未解決の指摘と重複していないか（重複なら既存の ID に経緯を足す）
- 未解決の指摘に状況の変化がないか

## 3. REVIEW.jsonl に記録する

**状況が変わったら、返答の前に記録する**（`/sync` まで先送りしない）。1行1JSONで、行は2種類。

### 指摘の行（1件1行。書き換える）

```jsonl
{"id":"R-001","status":"doing","title":"検索条件の初期値が未記載","target":"repos/x/docs/画面設計書.md 検索条件","action":"顧客の回答どおり、初期値を前月から当月までにして記載する","refs":["repos/x/docs/画面設計書.md:40-52"]}
```

（下の経緯の行の後の状態。回答待ちの間は `"status":"hold"` と `"waitingOn":"client"` だった）

- キーはこの順: `id`, `status`, `title`, `target`, `action`, `waitingOn`, `refs`（必須は先頭の4つ）。
- `id`: `R-` + 3桁の通し番号。スレッド内で共通、既存の最大+1。指摘の行は消さないので再利用は起きない。
- `status`: `open`（未対応） / `doing`（対応中） / `hold`（保留） / `resolved`（解決） / `withdrawn`（取り下げ）。
  - 回答があっても修正が残っていれば未解決のまま。疑問が回答だけで解消する場合は、根拠を経緯に書いてから `resolved` にできる。
- `title`: 指摘の短いタイトル。`target`: 対象の成果物（パス）と節名など。
- `action`: 次の対応（次に行うこと・待っている回答）。`resolved` と `withdrawn` では省いてよい。
- `waitingOn`: STATE.jsonl と同じ語彙（`human` / `client`）。
- `refs`: 今の該当箇所（`<ワークスペースからの相対パス>:<開始行>-<終了行>`）と参考資料。成果物が直って行がずれたら、今の位置に直す。
- 更新は ID で grep して該当行だけ Edit する。`grep -n '"id":"R-001","status"' _ops/threads/<thread-id>/<thread-id>-REVIEW.jsonl`

### 経緯の行（追記だけ。書き換えない）

```jsonl
{"id":"R-001","kind":"指摘","date":"2026-11-12 10:30","by":"user","text":"初期表示の絞り込み状態がない。検索結果の件数が想定できない","refs":["repos/x/docs/画面設計書.md:40-52"]}
{"id":"R-001","kind":"修正案","date":"2026-11-12 10:35","by":"ai","text":"「初期表示: 当月分で絞り込み」を検索条件の表に足す"}
{"id":"R-001","kind":"質問","date":"2026-11-12 10:40","by":"ai","text":"初期値を当月にしてよいか顧客に確認する"}
{"id":"R-001","kind":"回答","date":"2026-11-13 09:10","by":"client","text":"ユーザー経由。11/13の定例で回答。当月ではなく前月から当月まで"}
```

- キーはこの順: `id`, `kind`, `date`, `by`, `text`, `refs`, `commit`（必須は先頭の5つ）。
- `kind`（分類）:

  | kind | 書くこと |
  | --- | --- |
  | 指摘 | 問題と影響。指摘元が外部なら出典も |
  | 根拠 | 問題だと言える理由。短い原文の抜粋は「」で入れる |
  | 修正案 | そのまま適用できる具体的な修正 |
  | 質問 | 人間・顧客に尋ねたこと（保留の理由になる） |
  | 回答 | 人間・顧客からの回答・指示 |
  | 判断 | 決めた結論と理由。採用しなかった案もここに書く |
  | 修正 | 成果物をどう直したか |
  | 確認 | 何をどの範囲で確かめ、結果はどうだったか |
  | 再発 | 解決済の指摘を開き直した理由と場所 |
  | 訂正 | 過去の記録の誤り（どの日時の行が・どう誤りか） |
  | 規則提案 | RULES.md への追記を提案した内容 |

- `date`: `YYYY-MM-DD HH:mm`。コマンドで取得する（`date '+%Y-%m-%d %H:%M'` / `Get-Date -Format 'yyyy-MM-dd HH:mm'`）。
- `by`: 誰の発言・判断か。`user`（ユーザー） / `ai` / `client`（顧客） / `external`（外部レビュー）。ユーザー経由で伝わった顧客の回答は `client` にし、経路と出典（会議・メール・日付）を `text` に書く。
- `text`: 1行・200字くらいまで。収まらなければ**行を分ける**（`id`・`kind`・`date` を揃え、1行ずつ意味が通るよう論点ごとに分ける）。メモファイルを作って逃がさない。
- `refs`: 原文の位置（そのときの `path:行`）と参考資料（リポジトリの文書・`_ops/shared/` など）だけを指す。REVIEW のために作ったファイルは指さない。
- `commit`: 「修正」の行に付ける。修正前の原文は git の履歴で辿る。
- 原文の全文は REVIEW.jsonl に入れない（複数行はエスケープ事故の元）。人間向けの引用は未解決一覧を作るときに成果物から取る。

### 記録のしかた

- 経緯の行は sync の「2. 未記録の決定をログに足す」と同じ書き方（ヒアドキュメント推奨）で `>>` 追記する。値は1行・パスは `/` 区切り・引用符は「」。
- `status` と `action` は今の内容に書き換え、過去の回答や判断は経緯の行に残す。
- 方針が変わった・決めたことが覆ったら、新しい「判断」の行に、変更前の判断の日時と変更の理由を書く。記録そのものが誤っていたなら「訂正」の行を書く。どちらも前の行は直さない。
- 議論は途中を毎回書かない。**結論が出たとき・どちらかの立場が変わったとき・外部から回答が来たとき**に書く。
- 指摘に関わる決定は REVIEW.jsonl が正。ログ（`-log.jsonl`）にはスレッド全体の方針に関わるものだけ、`R-001` を参照して結論と理由を書く。
- 人間にしかできないことは、STATE.jsonl の task に `waitingOn` を付け、`title` か `detail` で `R-001` を指す（経緯は STATE に書き写さない）。

## 4. 未解決一覧を作り直す

REVIEW.jsonl を更新したら、`work/review/<thread-id>-review-pending.md` を作り直す。載せるのは `status` が `open` / `doing` / `hold` の指摘だけ。

`grep -E '"status":"(open|doing|hold)"' _ops/threads/<thread-id>/<thread-id>-REVIEW.jsonl`

各指摘は次の書式で書く。見出しはすべて必須で、回答待ちでもこの書式のまま。独自のセクションは足さない。

````markdown
# 未解決の指摘: <thread-id>

## R-001: <短いタイトル>

### 該当箇所

`<ワークスペースからの相対パス>:<開始行>-<終了行>`

```text
<該当行から直接取得した原文>
```

### 指摘内容

<引用した原文の何が問題で、どのような影響があるか>

### 修正案

1. <具体的な修正案、または判断が必要な確認事項>

### 次の対応

<今必要な修正・確認、回答待ちの相手と内容>
````

- 原文は**その都度ファイルを開いて**該当行をそのまま写し、書き出した後に元ファイルと照合する。記憶や REVIEW.jsonl の抜粋から書かない。要約・言い換え・パスだけで引用を代えない。
- 該当箇所が複数あれば、パスと原文の組を繰り返す。原文に ``` が含まれていれば、外側のフェンスを長くする。
- 過去の回答や完了後の確認の履歴は載せない（REVIEW.jsonl に残っている）。
- 解決・取り下げの根拠を REVIEW.jsonl に記録してから、その指摘を一覧から項目ごと消す。
- 未解決が1件も無ければ、見出しと「未解決の指摘はありません。」だけを残す。

書き終えたら `python _ops/schema/check.py <thread-id>` で、REVIEW.jsonl の書式と、未解決一覧の見出し・引用・載っている ID の過不足を確かめる（書式の機械的な定義は `_ops/schema/review.schema.json`。Python が無ければ飛ばす）。`ERROR` は直す。

チャットには、記録した指摘の ID と、未解決一覧のパス・件数を伝える。

## 5. 普遍的な指摘は RULES.md への追記を提案する

他のスレッドでも起きうるという確信が高い（目安として 70% 以上）指摘があれば、RULES.md への追記を**ユーザーに提案する**。提案するだけで、ここでは書かない。提案したら「規則提案」の行を足す。

判断基準（満たすものが多いほど確信が高い）:

1. 特定の設計書や画面に固有ではなく、他の設計書でも起きうる
2. RULES.md に似た規則がまだない
3. 同じ種類の指摘が複数回出ている

## 6. 指示に応じて RULES.md へ追記する

内容を直接指示されたとき、またはレビュー記録の指摘（例: R-001、R-003）から吸い上げるよう指示されたときだけ、`_ops/RULES.md` に書く。

- ドキュメント種類やセクションで階層化し、既存の構成に合う場所へ入れる。
- 個別の成果物に固有の内容は書かず、一般化した規則にする。
- 吸い上げた指摘には、追記した場所を「判断」の行（`by` は `user`）で残す。
