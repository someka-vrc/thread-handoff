# internal-review

対象は今のスレッド（`_ops/threads/<thread-id>/`）。指摘の記録先は `<thread-id>-REVIEW.md`（無ければ作る）。

ユーザーから誤りの指摘を受けただけのときは、1〜3 を飛ばして 4 から行う。

## 1. まっさらな視点でレビューする

REVIEW.md と RULES.md を読む前に、成果物だけを見てレビューする。先に読むと、記録済みの観点に引きずられて新しい問題を見落とすため。

## 2. 記録と規則を踏まえてレビューする

`_ops/RULES.md` と `<thread-id>-REVIEW.md` を読み、もう一度レビューする。

- RULES.md の規則に違反していないか
- 対応済の指摘が再発していないか
- 保留・未対応の指摘に、状況の変化がないか

## 3. レビューファイルに書き出す

`_ops/threads/<thread-id>/work/review/review-YYYYMMDD-HHmm.md` を作り、指摘を次の形式で書く（日時はコマンドで取得する）。チャットには、このファイルのパスと指摘の件数を伝える。

````markdown
# レビュー: <対象の成果物>

---

## R-001: <短いタイトル>

### 該当箇所

`<ワークスペースからの相対パス>:<行番号>`

```
<原文の引用>
```

（該当箇所が複数あれば、パスと引用を繰り返す）

### 指摘内容

<何が問題で、なぜ問題か>

### 修正案

1. <案>
2. <別の案>

---
````

- 該当箇所は全件、ワークスペースからの相対パス（`/` 区切り）と行番号で示す。
- 引用はファイルを開いて原文のまま写す。記憶で書かない。
- 指摘内容は、該当箇所を見ていない人にも分かるように書く。
- 修正案は、そのまま適用できる具体的な内容で書く。

## 4. REVIEW.md に追記・状態更新する

対象の成果物ごとに見出しを切り、指摘を次の形式で書く。詳細はレビューファイルに任せ、ここには状態の管理に必要なことだけを書く。

```markdown
# REVIEW: <thread-id>

## 対象: <成果物のファイル名>

### R-001 <指摘の要約>
- 指摘: <何が問題か（1行）>
- 詳細: _ops/threads/<thread-id>/work/review/review-YYYYMMDD-HHmm.md（レビューファイルがあるとき）
- 指摘元: ユーザー指示（YYYY-MM-DD） | AIのセルフレビュー（YYYY-MM-DD）
- 対応: <どう直したか・何待ちか>
- 状態: 未対応 | 保留（理由） | 対応済
```

- 番号はスレッド内の通し番号（既存の最大+1。再利用しない）で、レビューファイルと同じものを使う。
- 既存の指摘が進んだら、該当の `対応` と `状態` を更新する。
- 指摘元はユーザーとAIを区別する。
- ユーザーやクライアントの回答待ちは `保留` にする。人間にしかできないことは、STATE.jsonl の task にも `waitingOn` を付ける。

## 5. 普遍的な指摘は RULES.md への追記を提案する

他のスレッドでも起きうるという確信が高い（目安として 70% 以上）指摘があれば、RULES.md への追記を**ユーザーに提案する**。提案するだけで、ここでは書かない。

判断基準（満たすものが多いほど確信が高い）:

1. 特定の設計書や画面に固有ではなく、他の設計書でも起きうる
2. RULES.md に似た規則がまだない
3. 同じ種類の指摘が複数回出ている

## 6. 指示に応じて RULES.md へ追記する

内容を直接指示されたとき、またはレビュー記録の指摘（例: R-001、R-003）から吸い上げるよう指示されたときだけ、`_ops/RULES.md` に書く。

- ドキュメント種類やセクションで階層化し、既存の構成に合う場所へ入れる。
- 個別の成果物に固有の内容は書かず、一般化した規則にする。
