# kickoff

作業の単位は**スレッド**。スレッドのファイルは `_ops/threads/<thread-id>/` にある。

## 1. スレッドを決める

- ユーザーがスレッドIDを指定したら、それを使う。
- 指定が無ければ、スレッドの一覧を `title` つきで見せて、どれをやるか尋ねる（スレッドが1つだけならそれを使う）。
  `grep -H '"type":"meta"' _ops/threads/*/*-STATE.jsonl`
- ユーザーが新しいスレッドを指示したら（または該当するスレッドが無ければ）、下の「新しいスレッドの立ち上げ」に従う。
- スレッドが決まったら（新しいスレッドなら作成後に）、チャットセッションのタイトルを変更できるツールがあれば、タイトルを変更する。無ければ何もしない。
  - `<title>:<指示内容>(<thread-id>)`（`title` は STATE.jsonl の `meta`）。
  - 指示内容がない場合は `<title>(<thread-id>)`。

## 2. 読む

次の4つを読む。これ以外（他のスレッド、`work/`、`shared/`、`archive/`）は必要になるまで読まない。

1. `_ops/threads/<thread-id>/<thread-id>-STATE.jsonl` 全文
2. `_ops/RULES.md` 全文（**何かを編集したりコマンドを叩いたりする前に必ず読んでおく**）
3. `_ops/threads/<thread-id>/<thread-id>-log.jsonl` の末尾20行（`tail -n 20`。全文は読まない）
4. `_ops/threads/<thread-id>/<thread-id>-REVIEW.jsonl` の未解決の指摘の行だけ（全文は読まない）
   `grep -E '"status":"(open|doing|hold)"' _ops/threads/<thread-id>/<thread-id>-REVIEW.jsonl`
   - 今回の対象の成果物に関係する指摘は、経緯の行も読む（`grep '"id":"R-001","kind"' …`）。
   - **今回の指示が新しいレビューなら 4 は読まない**。internal-review の手順どおり、成果物を見てから記録と照合する。

`-HUMAN.md` は、関係しそうなときに読む。

## 3. 今回の範囲を決める

- ユーザーの新しい指示があれば、**作業を始める前にまっさきに** STATE.jsonl へ `doing` の task として書く。
- 指示が無ければ、`status` が `doing` のものをやる。無ければ `next`、それも無ければ `later` から候補を提案して、ユーザーに選んでもらう。
- `waitingOn` があって進められないものは、その旨を伝えて別の作業を選ぶ。
- note の `text` は、今回の進め方として従う。

範囲を1〜3行でユーザーに伝え、そのまま始める。

## 4. STATE.jsonl の書き方

- 1行1JSON。行の種類は先頭のキーで決まる: `{"type":"meta",…}` / `{"type":"note",…}` / `{"id":…}`（task）。
- meta は1行目。
  - 必須キー: `type`, `thread`, `title` 。`title` は、このスレッドが何のためのものかを1行（20字くらいまで）で書く。
  - 任意キー: `ticket`, `branch`, `worktree`
- task のキーはこの順: `id`, `status`, `title`, `detail`, `dependsOn`, `waitingOn`, `refs`（必須は先頭の3つ）。
  - `id`: 3桁の通し番号（既存の最大+1。再利用しない）。子は `002-001`。孫（`002-001-001`）は作らない。
  - `status`: `doing` / `next` / `later`。
  - `title` は1行。`detail` は2文・150字くらいまで。長い手順や論点は `_ops/threads/<thread-id>/work/<目的>/` にメモを置き、`refs` で指す。
  - `dependsOn`: 先に終わらせる task の ID の配列。存在しない ID は満たされたものとして扱う。
  - `waitingOn`(待ち理由): `human`(ユーザー) / `client`(顧客)。
  - `refs`: ワークスペースのトップからの相対パスの配列。
- note は `text`（100字くらいまで）と、`until`（効いている間の条件）か `promote`（恒久的な知識の移行先）の**どちらかが必須**。
- **更新は1行だけ**。ID で grep して該当行を Edit する。ファイル全体を読み直して書き直さない。昇格は `status` の置換、新規は最大ID+1 で末尾へ追記、完了は行ごと消す。完了したこと・経緯は書かない（判断はログ）。
- **値は1行に収める**（`title` / `detail` / `text` / `until` など。改行を入れない。JSON の `\n` も使わない）。複数行になる内容は `_ops/threads/<thread-id>/work/<目的>/` にメモを置き、`refs` で指す。
- **パスは `/` 区切りで書く**。`\` は使わない（JSON のエスケープとシェルのエスケープが重なって、コマンドが壊れる）。Windows のパスも `D:/develop/…` の形で書く。
- **値の中の引用符は「」を使う**。`"` と `'` は使わない。どうしても必要なときだけ、JSON では `\"` と書く（このときだけ `\` を使ってよい）。シェルで追記するときのエスケープは sync の「2. 未記録の決定をログに足す」を見る。
- 常に100行未満。ユーザーが STATE.jsonl を直接編集したと言ったときは、全文を読み直してから更新する。
- キー・キー順・値の語彙と書式の機械的な定義は `_ops/schema/state.schema.json`。sync と handoff の最後に `python _ops/schema/check.py <thread-id>` で確かめる（Python が無ければ飛ばす）。

## 5. 作業中に守ること

- **STATE.jsonl は毎回更新する**: 新しい指示・決定・完了・方針転換があったら、返答の前に書く。変化がなければ何もしない。
- 覚えておきたくなったことは、次の表の行き先に書く。**note に何でも書かない**。

  | 書きたくなったこと                                                       | 書く場所                                     |
  | ------------------------------------------------------------------------ | -------------------------------------------- |
  | やるなと言われた・直せと言われた（誤りの指摘）、指摘への回答・修正・確認 | REVIEW.jsonl（internal-review スキルに従う） |
  | 指摘に関わらない、何かを決めた・採用しなかった案がある                   | ログ（`-log.jsonl`）                         |
  | 次にやること・後でやること                                               | task                                         |
  | しばらくの進め方・状況（タスク横断）                                     | note + `until`                               |
  | ずっと守るべき・恒久的な知識                                             | note + `promote`                             |

- ログと `-HUMAN.md` は、途中で毎回書かなくてよい。sync か handoff でまとめて書く。
- REVIEW.jsonl と未解決一覧は、レビュー指摘の状況（回答・指示・修正・確認・保留理由）が変わったら、返答の前に更新する（internal-review の 3〜4）。
- 人間にしかできないこと（確認・問い合わせ・手作業）が出たら、task に `waitingOn` の `human` を付ける（HUMAN.md には sync か handoff で足す）。
- 一時的なスクリプトや生成物は、このスレッドだけで使うなら `_ops/threads/<thread-id>/work/<目的>/`、複数スレッドで使い回すなら `_ops/work/<目的>/` に置く。`_ops/work/` の他のスレッドが作ったフォルダは書き換えない。
- `_ops/shared/` と `_ops/RULES.md` は書き換えない（shared はユーザーが置く。RULES はユーザーの指示があるときだけ internal-review が書く）。`_ops/schema/` も、ユーザーの指示があるときだけ書き換える（チェックを通すためにスキーマを緩めない）。
- 他のスレッドのファイルは書き換えない。
- 区切り（タスクが終わった・方針が変わった・会話が長くなった）で、ユーザーに `/sync` を勧めてよい。

## 新しいスレッドの立ち上げ

1. `_ops/RULES.md` を全文読む。
2. 何のためのスレッドかが分からなければ尋ねる。スレッドIDも `title` も推測で作らない。
3. スレッドIDと `title` を決める。スレッドIDは英小文字・数字・ハイフンの短い名前（チケット番号でもよい）。
   - ユーザーがスレッドIDを指定し、`title` も指示から明らかなら、確認せずに進む。
   - 推測が入るものは提案して、確認が取れてから作る。
4. `_ops/threads/<thread-id>/` と `work/` を作り、「作成ファイル」セクションの通りにファイルを作る。
5. 具体的な作業の指示があれば、STATE.jsonl に `doing` の task として書き込んでから始める。無ければ `meta` だけで止めて、何から始めるか尋ねる（「スレッドを立ち上げる」のような task は作らない）。

### 作成ファイル

`<thread-id>-STATE.jsonl`:

```jsonl
{"type":"meta","thread":"<thread-id>","title":"<何のためのスレッドか>"}
```

`<thread-id>-HUMAN.md`:

```markdown
# HUMAN: <thread-id>

人間（ユーザー）にしかできないこと。済んだら行ごと消してよい（AIは消されたものを完了とみなす）。

```

`<thread-id>-REVIEW.jsonl` と `work/review/<thread-id>-review-pending.md` は、最初の指摘を記録するときに internal-review が作る。
`<thread-id>-log.jsonl` は空で作る（最初の判断を書くときに `>>` で作られるので、無くてもよい）。
