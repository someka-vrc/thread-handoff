# Thread Handoff 設計

Thread Handoff が何かは [README.md](../README.md) を参照。Memory Bank / GSD（Get Shit Done）/ Project Continuity / agent-handover / self-improving / ADR（Architecture Decision Record）などとの類似・合わせ技で、プロアクティブエージェントのアイデアも意識している。

このファイルには、実ファイルを見ても分からない設計の理由と判断だけを書く。人間の操作は [README.md](../README.md) の「使い方」、経緯と見送った案の詳細は [HISTORY.md](HISTORY.md)。

## 前提: スレッド

ワークツリー・ブランチ・チケットは運用の前提にしない。プロジェクトによっては使えないため（振られたタスクごとにスレッドを切って作業するだけ、など）。

- 作業の単位を**スレッド**と呼ぶ。ワークツリー・ブランチ・チケットは、スレッドに紐づく属性として扱う。任命された複数のタスクを1スレッドでまとめてやることもある。
- スレッドIDは自由に決める（チケット番号、ブランチ名の一部、任意の短い名前）。基本的にはセッションのメイントピックに対応する。ディレクトリ名とファイル名の接頭辞に使う。

## ワークスペースの配置

トップ階層の「ワークスペース」は、プロジェクトフォルダそのものではない。

```
ワークスペース/
  AGENTS.md
  .agents/skills/
  _ops/
  repos/<project>/            ← 例。階層・個数・名前は任意
  repos/<project>.worktrees/  ← 例
```

- **直下に単一プロジェクトを置くと効果が薄い。** 並行作業のためにワークツリーを切ると、その作業場所がワークスペースの外になる。エージェントにワークスペース外を信頼させるのは面倒で、散らかりもする。プロジェクトをワークスペース内に並べれば、ワークツリーも中に置ける。
- **何でも入れられるようにする。** プロジェクトや資料が1か所に揃えば、まとめて作業したり、並行作業したりできる。
- **ワークツリーなら「空気を読める」。** 自分や他人の未マージのブランチを覗いて、矛盾のチェックやコンフリクトの事前対策ができる。ブランチに乗っている資料は、`shared/` に置くよりワークツリーで見たほうが鮮度を保ちやすい。
- **ワークスペース自体を git 管理する必要はない。** 各プロジェクトが個別に git を持つ。
- **エージェントはワークスペースで起動する。** 各プロジェクトのルートでは起動しない。skills と `_ops/` をトップから参照するため。

## ファイルの役割と設計理由

### HUMAN.md

人間タスクをチェックボックスで書く。終わったものは整理時に消し、短く保つ。

### STATE.jsonl

以降のセッションでやることを書く。

- **TODO.md は設けない。** 思いつきでタスクを積み増すことが少ない運用のため、STATE に担わせる。
- **jsonl にする理由:** 実体は TODO リストなので構造化した。ID で grep して該当行だけ Edit できるので、AI が置換のために全文を読み直さなくて済む。スレッド横断の集計も grep でできる。
- **値を1行に収め、パスを `/` 区切りにし、引用符を「」にする理由:** JSON とシェルのエスケープが重なると、コマンドが壊れるため。現場で事故が多発した。ログも同じ。
- **`meta` に書くのは `title` と紐付けだけ。** スレッドIDだけでは何のためのスレッドか分からないので、`title` に1行で書く。一覧からスレッドを選ぶ手がかりにもなる。ほかは外部との紐付けを固定キーで書き、散文は入れない。プロジェクトごとに属性が変わっても構造は変えない。
- **note に `until` か `promote` を必須にする理由:** AI は「忘れたくない」「同じ指摘を繰り返したくない」という動機で、自由記述にいくらでも書いてしまう。事前に禁止しても守れず、逆に重要なことを落とす。そこで好きに書かせたうえで handoff で刈り取る。書く時点で期限か移行先を決めさせるのが、そのまま分類になる。

テンプレートのスレッドは空で、kickoff の書式説明には全種類の行が揃った実例がないため、例をここに置く（patto-v の STATE から写した抜粋。note の2行は説明用の架空）。

```jsonl
{"type":"meta","thread":"main","title":"patto-v の機能の仕上げ","branch":"main","worktree":"repos/main"}
{"type":"note","text":"今は仕上げフェーズ。新機能は足さず、確認と不具合修正だけ","until":"004 の配布方法が決まるまで"}
{"type":"note","text":"check.cs で表の動画を一通り変換できる（work/variety/。試しの動画は work/samples/）","promote":"repos/main/docs/TESTING.md"}
{"id":"001","status":"doing","title":"NVENC 対応を実機の動画で確認してもらう","detail":"コミット済み（main、未push）。cq 22/25/30 は合成動画で決めたので、指摘があれば直す","waitingOn":"human"}
{"id":"002","status":"next","title":"mkv 出力の音声を aac にするか決める","detail":"既定の vorbis だと Windows 標準の再生で鳴らない恐れ"}
{"id":"002-001","status":"next","title":"aac にしてよいかユーザーに確認","waitingOn":"human"}
{"id":"002-002","status":"next","title":"mkv で映像・音声があるとき -c:a aac にする","detail":"FfmpegCommandBuilder とテストを直す","dependsOn":["002-001"]}
{"id":"004","status":"later","title":"配布方法を決める（MSIX か zip・インストーラ）","detail":"winapp init は未実施。インストーラでも ffmpeg への誘導・自動インストールはしない（決定済み）","refs":["repos/main/docs/PRODUCT.md"]}
```

### REVIEW.jsonl と未解決一覧

スレッド固有のレビュー指摘を、永続記録の `<thread-id>-REVIEW.jsonl` と、人間向けの未解決一覧 `work/review/<thread-id>-review-pending.md` の2ファイルで管理する。「クライアントに質問中だから待って」のようなペンディングも、ここで扱う。

- **2ファイルに固定する理由:** 実施日時や成果物ごとにファイルを分けると、増えるほど今の確認先が分からなくなるため。日時はファイル名ではなく中身（経緯の行の `date`）に持たせる。
- **永続記録と一覧を分ける理由:** 人間が見たいのは今片付いていないものだけだが、片付いたものを消すと根拠や経緯まで失われる。経緯はすべて REVIEW.jsonl に残し、一覧はそこから作り直せる派生ビューにする。一覧は消しても作り直せるので、消してよい `work/` に置ける。
- **jsonl にする理由:** 更新の動きが「状態を今の内容に書き換える」と「経緯を足していく」の2つしかなく、STATE.jsonl（ID で grep して1行 Edit）とログ（`>>` で追記）の書き方がそのまま当てはまる。人間は一覧を読むので、記録は機械向けでよい。
- **行を2種類に分ける理由:** 詳細を配列で1行に持たせると、経緯が増えるたびに長い行を読み直して書き換えることになり、崩す危険が高く、追記専用の安全性も失う。指摘の行は書き換え、経緯の行は追記だけにして、「過去の経緯の行は書き換えない」の1規則で経緯を守る。2列目のキー（`status` か `kind`）で行の種類を見分けられる。
- **原文の全文を入れない理由:** 複数行の引用は「値は1行」の規則とぶつかり、`\n` のエスケープが現場で事故が多発した形そのものになる。人間向けの引用は一覧を作るたびに実ファイルから取り、修正前の原文は「修正」の行の `commit` から git の履歴で辿る。git に乗らない資料の全文は残らないと割り切り、抜粋だけを残す。
- **`refs` を原文の位置と参考資料に限る理由:** 長くなった議論や引用の退避先としてファイルを作らせると、散らかったうえに消してよいか分からなくなる（日時付きレビューファイルの問題の再来）。`text` に収まらなければ行を分ける。経緯の行は追記するだけなので、行が増えても編集で崩れない。
- **次回IDを記録しない理由:** 指摘の行は消さないので、既存の最大+1で再利用は起きない。記録した値と実際がずれる危険もなくなる。
- **`status` を英語、`kind` を日本語にした理由:** `status` は grep の条件に使うので、STATE と同じく英語にしてシェルでの日本語照合を避けた。`kind` は種類が多く、人間が覗いたときの読みやすさを優先した。
- **`by` に `client` / `external` を置く理由:** 顧客とのやり取りで決まった・覆ったことを、AI とユーザーの議論と区別して残すため。ユーザー経由で伝わった回答は、発言者を `by`、経路と出典を `text` に書く。
- **指摘に関わる決定は REVIEW.jsonl を正とする:** ログにも書くと二重記録になり、片方だけ更新されてずれる。ログには、スレッド全体の方針に関わるものだけを ID の参照つきで書く。
- **状況が変わったら返答の前に更新させる理由:** 回答・修正のたびに人間が「記録して」「一覧から消して」と頼む手間が、現場で繰り返し発生していたため。途中の必須更新を STATE だけに絞った方針（「運用上の注意」）の例外だが、レビューの状況が変わるのは人間の回答や修正の完了といったはっきりした出来事に限られ、毎ターンの負担にはならないと見ている。
- **一覧の書式を固定し、原文の引用を必須にする理由:** 現場で見出しを任意にしたところ、原文の引用が省かれる退行が起きた。リンクや要約だけだと、人間がファイルを開かないと判断できない。

### 独立レビューの順序

internal-review は、過去の記録（REVIEW.jsonl）を見ずに成果物と一次資料でレビューし、その後で記録と照合する。v1.0.0 は「REVIEW.md と RULES.md を読む前に」としていたが、kickoff は作業の前に RULES.md を読ませるので、手順どうしが衝突していた。RULES.md は観点を引きずるものではなく守るべき規則なので、既に読んだものをそのまま適用する。

### log.jsonl

意思決定ログ。スレッドごとに分けて、追記だけする。

- **スレッド別にする理由:** 共有の1ファイルだと、並行作業で唯一の衝突点になるため。
- **`>>` で1行だけ足す理由:** ファイル全体を読んで書き直さないため。
- **`by` で書き手を区別する理由:** ユーザーの指示か AI の推測かで、後から信頼してよい度合いが違うため。
- **途中で毎回書かせない理由:** 追記専用なので、漏れても害が小さく handoff で拾える。

### RULES.md

作業時の共通規則（共通的なハマりどころ、繰り返し指摘されること）。新規成果物を作るときに参照させて、繰り返しの指摘を抑える。

個別のレビュー指摘を受けたときに書き込む場所ではない。書くのはユーザーの指示があるときだけで、人間のゲートで守る。

### shared/

スレッド横断で使える、人間が置く参考資料の置き場。AI は読むだけ。

- **用途別のサブフォルダに入れる理由:** 直下を散らかすと掃除の判断ができないため。
- **RULES.md から指す理由:** kickoff は RULES.md を全文読むので、shared/ 自体を毎回読ませる必要はなく、中身が増えても読み込みコストは増えない。
- **弱点は古くなること。** 置いた時点のスナップショットなので、RULES.md に取得元と取得日を書いて補う。

### work/（スレッド内・スレッド共通）

AI が置く一時的なスクリプトや生成物の置き場。目的ごとにサブフォルダを切る。そのスレッドだけで使うなら `<thread-id>/work/`、複数スレッドで使い回すなら `_ops/work/`。

スレッド内の work/ は、不要になったら消してよい。kickoff では読まないので、次のセッションで必要なものは STATE.jsonl の `refs` か `detail` に場所を書いておく。

### archive/

古いスレッドの退避先。移すのは人間で、AI は判断しない。

### schema/（スキーマとチェックスクリプト）

STATE / REVIEW / log の書式を JSON Schema で定義し、`check.py` で確かめる。**オプション**であり、使うなら Python が要る、という建付けにして「基本的にツール不要」は守る。スキルのチェック手順も、Python が無ければ飛ばすだけにしている。

- **作った理由:** スレッドが増えると、AI にスレッド横断のサマリーを頼むことが増えるが、書式が保証されていないと AI は全行を丁寧に読むことになる。チェックが通ることを保証にすれば、件数の集計などは単純なスクリプトで済む。
- **JSON Schema にした理由:** 標準の形式なので、AI も他のツールも定義として読める。サマリーを組む人は、スキーマだけを見ればよい。
- **バリデータを自前で持つ理由:** オプションを使うときに要るものを Python だけにとどめるため。Python の標準ライブラリに JSON Schema のバリデータは無いので、jsonschema などのパッケージを入れずに、スキーマで使っているキーワードだけを `check.py` で解釈する。スキーマは標準の JSON Schema として書いてあるので、汎用のバリデータでも検証できる（独自キーワードは無視される）。
- **解釈しないキーワードがあれば止める理由:** 自前のバリデータは、知らないキーワードを黙って無視すると、スキーマに足した規則が効いていないのに通ってしまう。そこでスキーマを先に調べ、未対応のキーワード・`type`・参照先の無い `$ref` があれば、記録を確かめずに終了コード 2 で止める。キーワードを足すときは `check.py` に実装もする。
- **Python にした理由:** JSON を素直に扱え、bash と pwsh のどちらからも同じコマンドで呼べる。PowerShell は Windows 以外で導入が要り、シェルスクリプトは jq に頼ることになる。
- **独自キーワードを2つ足した:** キー順は JSON Schema で表せないので `x-keyOrder`（`properties` の順に並べる）。ID で grep して1行 Edit する運用はキー順の固定が前提のため、エラーにする。字数の目安は守れなくても壊れないので `x-warnMaxLength` で警告にとどめる。
- **行をまたぐ規則はスクリプトに置いた:** meta が1行目、ID の重複、経緯の行の ID に指摘の行があるか、未解決一覧の過不足・見出し・原文の引用など。JSON Schema は1行（1つの JSON）しか見られないため。
- **meta だけ未知のキーを許す:** README の「プロジェクトに合わせる」で属性を足す前提なので、足すたびにスキーマを直させない。ほかの行は未定義のキーをエラーにし、AI が独自の欄を増やすのを防ぐ。
- **書式の説明はスキルに残した:** スキーマは機械向けで、キーの意味や書くときの判断はスキルにしか書けない。定義が2か所になるが、機械的に確かめられる部分はスキーマを正とし、ずれたらチェックで気づける。書式を変えるときは、スキル・スキーマの両方を直す。
- **フックで自動実行しない:** フックで強制しない方針（AGENTS.md の項）と同じ。sync・handoff・internal-review の最後に AI が実行し、人間も好きなときに実行できる。Python が無い環境では飛ばしてよい。
- **AI にスキーマを書き換えさせない:** チェックを通すためにスキーマを緩めるのを防ぐ。RULES.md と同じく、ユーザーの指示があるときだけ。

## スキルに書かない判断

### AGENTS.md

- 核心だけを置き、詳細はスキルに任せる。会話中に読んだスキル本文は長い会話や圧縮で薄まりやすいが、AGENTS.md（CLAUDE.md）は残りやすい、という見立て（仮説。実測はしていない）。
- 1行・`/` 区切りの規則は、守られないとコマンドが壊れる事故が現場で多発したため、核心としてここにも置いた。REVIEW.jsonl も同じ規則に入れた。
- レビュー指摘を返答の前に記録する規則も、核心として置いた。kickoff を読んだ後の長い会話で回答や修正が続くとき、スキル本文が薄まっていても守られるようにするため。
- ターン末に「STATE: 更新済 / 変更なし」を1行出させる案は、毎ターン出て鬱陶しいので見送り。AGENTS.md と sync で足りなければ試す。
- フックで強制する案は、ベンダー差とメンテの重さから避ける。入れるなら「STATE.jsonl が長く更新されていなければリマインド」程度の補助にとどめる。

### kickoff

- 立ち上げ手順で推測を禁じるのは、でっち上げたスレッドIDや `title`、無意味な task は形式としては正しく、後から気づきにくいため。ただし、毎回確認すると煩わしいので、確認するのは推測が入るときだけにする。
- 書式の説明の正は kickoff の「4. STATE.jsonl の書き方」（機械的に確かめられる部分の正は `state.schema.json`）。sync には説明を再掲せず、task の行の例を1行だけ置いている。読み込みを増やさないまま、kickoff の内容が圧縮で薄れたときや、STATE に書き写す task の行が無いときでも正しい書式で書けるようにするため。kickoff の書式を変えたら、sync の例も直す。
- 「5」の行き先表は、禁止ではなく案内。AI が「覚えておきたい」と感じる動機ごとに正規の行き先を用意して、note への流入を減らす狙い。誤りの指摘（とそれに関わる決定）は REVIEW.jsonl、それ以外の決定はログ、という分担が前提で、実装系の指摘が REVIEW.jsonl に馴染むかはプロジェクトで確かめる。
- REVIEW.jsonl は、未解決の指摘の行だけを grep で読ませる。永続記録は解決済も含めて増え続けるので、全文を読ませると読み込みが膨らむ。新しいレビューを頼まれたときに読ませないのは、独立レビューの順序（上の「独立レビューの順序」）を守るため。
- ログと HUMAN を途中で毎回書かせないのは、STATE は漏れると次のセッションが壊れるが、ログは漏れても handoff で拾えるため。必須を STATE だけに絞ったほうが守られやすい。
- スレッドの切り方を RULES.md に書かないのは、kickoff のときにやることが RULES.md にあると、スキルと規則の間で参照が絡むため。プロジェクトごとに kickoff を書き換える前提なので、テンプレートの kickoff には一例を書き込まない。
- jsonl は1行が長くなりがちなので、「100行未満」が行数より文字量で重くなるかもしれない。使って確かめる。

### sync

- 「読み込みなし」ではなく「該当行の grep だけ」。置換には正確な現在の行が要るので、ID で grep して1行 Edit できるよう、キー順と ID を固定している。
- 呼ぶのは人間（または AI が勧める）。自動化はしない。
- 人間が STATE.jsonl を直接編集したと言ったときだけ全文を読み直す。それ以外で全文を読ませると、sync の安さが失われる。
- REVIEW.jsonl は sync での更新を前提にしない。sync では今回進んだ指摘の記録漏れだけを確かめる。sync に任せると、呼ばれるまで一覧が古いままになり、人間が更新を頼む手間が戻ってくるため。
- 引用符は「」を基本にする。bash のエスケープ例はサンドボックスで確かめ済み（ヒアドキュメントと printf の結果が一致し、JSON として読める）。PowerShell の例は実行していないので、実機で確かめる。
- ログの追記はヒアドキュメント（`<<'EOF'`）を勧める。シェルのエスケープが要らず、`'` も気にしなくてよい。`\"` が、`\` を使ってよい唯一の例外。

### handoff

- handoff = sync + 終了処理（次のセッションでやることの決定・note の刈り取り・点検）。sync の手順は重複させず参照にした。
- 刈り取りは「提案 → 番号で承認」で、移行先への書き込みは承認後だけ。RULES.md を人間のゲートで守る方針と同じ考え方。承認なしで終わった handoff は、note が残るだけで壊れない。
- note の上限（5件・各100字）は、セッション中は縛らず、handoff の点検でだけ見る。禁止は守れないので、書いた後に見る。
- 次のセッションへの引き継ぎでは、レビューに関わる作業を指摘の ID で指させる。未解決一覧は作り直しで項目が消えるので、そちらを指すと参照が切れる。

## 運用上の注意

- **並行してもぶつからないはず。** スレッド固有のファイル（HUMAN / STATE / REVIEW / log / 未解決一覧）は書き手がそのスレッド内に閉じていて、共有ファイル（RULES.md、shared/）は人間の指示・操作でしか変わらない。
- **`_ops/schema/` はテンプレートの一部。** スレッドの記録ではないので、並行作業の衝突点にはならない（書き換えるのはユーザーの指示があるときだけ）。
- **`_ops/work/` は例外。** 複数スレッドが書ける唯一の AI 書き込み領域なので、目的ごとのサブフォルダに分け、他のスレッドが作ったフォルダは書き換えない（案）。
- **更新忘れの懸念。** 長い会話や安いモデルだと、STATE.jsonl やログの更新を忘れる。STATE が漏れると次のセッションが壊れるので、途中の必須更新は STATE.jsonl だけに絞り（ログと HUMAN は sync / handoff でまとめて。例外はレビューの状況が変わったときの REVIEW.jsonl と未解決一覧）、核心を AGENTS.md に数行で置き、区切りで `/sync` を呼ぶ。
