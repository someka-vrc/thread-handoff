# Thread Handoff 設計

Thread Handoff が何かは [README.md](../README.md) を参照。Memory Bank / GSD（Get Shit Done）/ Project Continuity / agent-handover / self-improving / ADR（Architecture Decision Record）などとの類似・合わせ技で、プロアクティブエージェントのアイデアも意識している。

このファイルには、実ファイルを見ても分からない設計の理由と判断だけを書く。人間の操作は [README.md](../README.md) の「使い方」、経緯と見送った案の詳細は [HISTORY.md](HISTORY.md)。

## 何を正とするか

実体は [workspace/](../workspace/) のテンプレート。内容が重なったら実ファイルを正とし、ここには同じ内容を書かない。

| 知りたいこと | 正とする場所 |

| 読む順番、STATE.jsonl の書式、書きたくなったことの行き先、スレッドの立ち上げ方、HUMAN.md の雛形 | [kickoff](../workspace/.agents/skills/kickoff/SKILL.md) |

## 前提: スレッド

ワークツリー・ブランチ・チケットは運用の前提にしない。プロジェクトによっては使えないため（振られたタスクごとにスレッドを切って作業するだけ、など）。

- 作業の単位を**スレッド**と呼ぶ。ワークツリー・ブランチ・チケットは、スレッドに紐づく属性として扱う。任命された複数のタスクを1スレッドでまとめてやることもある。
- スレッドIDは自由に決める（チケット番号、ブランチ名の一部、任意の短い名前）。基本的にはセッションのメイントピックに対応する。ディレクトリ名とファイル名の接頭辞に使う。

## ワークスペースの配置

トップ階層の「ワークスペース」は、プロジェクトフォルダそのものではない。

```
ワークスペース/
  AGENTS.md
  .agents/skills/
  _ops/
  repos/<project>/            ← 例。階層・個数・名前は任意
  repos/<project>.worktrees/  ← 例
```

- **直下に単一プロジェクトを置くと効果が薄い。** 並行作業のためにワークツリーを切ると、その作業場所がワークスペースの外になる。エージェントにワークスペース外を信頼させるのは面倒で、散らかりもする。プロジェクトをワークスペース内に並べれば、ワークツリーも中に置ける。
- **何でも入れられるようにする。** プロジェクトや資料が1か所に揃えば、まとめて作業したり、並行作業したりできる。
- **ワークツリーなら「空気を読める」。** 自分や他人の未マージのブランチを覗いて、矛盾のチェックやコンフリクトの事前対策ができる。ブランチに乗っている資料は、`shared/` に置くよりワークツリーで見たほうが鮮度を保ちやすい。
- **ワークスペース自体を git 管理する必要はない。** 各プロジェクトが個別に git を持つ。
- **エージェントはワークスペースで起動する。** 各プロジェクトのルートでは起動しない。skills と `_ops/` をトップから参照するため。

## ファイルの役割と設計理由

### HUMAN.md

人間タスクをチェックボックスで書く。終わったものは整理時に消し、短く保つ。

### STATE.jsonl

以降のセッションでやることを書く。

- **TODO.md は設けない。** 思いつきでタスクを積み増すことが少ない運用のため、STATE に担わせる。
- **jsonl にする理由:** 実体は TODO リストなので構造化した。ID で grep して該当行だけ Edit できるので、AI が置換のために全文を読み直さなくて済む。スレッド横断の集計も grep でできる。
- **値を1行に収め、パスを `/` 区切りにし、引用符を「」にする理由:** JSON とシェルのエスケープが重なると、コマンドが壊れるため。現場で事故が多発した。ログも同じ。
- **`meta` に書くのは `title` と紐付けだけ。** スレッドIDだけでは何のためのスレッドか分からないので、`title` に1行で書く。一覧からスレッドを選ぶ手がかりにもなる。ほかは外部との紐付けを固定キーで書き、散文は入れない。プロジェクトごとに属性が変わっても構造は変えない。
- **note に `until` か `promote` を必須にする理由:** AI は「忘れたくない」「同じ指摘を繰り返したくない」という動機で、自由記述にいくらでも書いてしまう。事前に禁止しても守れず、逆に重要なことを落とす。そこで好きに書かせたうえで handoff で刈り取る。書く時点で期限か移行先を決めさせるのが、そのまま分類になる。

テンプレートのスレッドは空で、kickoff の書式説明には全種類の行が揃った実例がないため、例をここに置く（patto-v の STATE から写した抜粋。note の2行は説明用の架空）。

```jsonl
{"type":"meta","thread":"main","title":"patto-v の機能の仕上げ","branch":"main","worktree":"repos/main"}
{"type":"note","text":"今は仕上げフェーズ。新機能は足さず、確認と不具合修正だけ","until":"004 の配布方法が決まるまで"}
{"type":"note","text":"check.cs で表の動画を一通り変換できる（work/variety/。試しの動画は work/samples/）","promote":"repos/main/docs/TESTING.md"}
{"id":"001","status":"doing","title":"NVENC 対応を実機の動画で確認してもらう","detail":"コミット済み（main、未push）。cq 22/25/30 は合成動画で決めたので、指摘があれば直す","waitingOn":"human"}
{"id":"002","status":"next","title":"mkv 出力の音声を aac にするか決める","detail":"既定の vorbis だと Windows 標準の再生で鳴らない恐れ"}
{"id":"002-001","status":"next","title":"aac にしてよいかユーザーに確認","waitingOn":"human"}
{"id":"002-002","status":"next","title":"mkv で映像・音声があるとき -c:a aac にする","detail":"FfmpegCommandBuilder とテストを直す","dependsOn":["002-001"]}
{"id":"004","status":"later","title":"配布方法を決める（MSIX か zip・インストーラ）","detail":"winapp init は未実施。インストーラでも ffmpeg への誘導・自動インストールはしない（決定済み）","refs":["repos/main/docs/PRODUCT.md"]}
```

### REVIEW.md

スレッド固有のレビュー指摘をメンテする。レビュー対象、指摘内容、対応状況のほか、「クライアントに質問中だから待って」のようなペンディングも管理する。指摘の詳細（該当箇所の引用や修正案）は `work/review/` のレビューファイルに書き、REVIEW.md は状態を管理する台帳に徹する。

### log.jsonl

意思決定ログ。スレッドごとに分けて、追記だけする。

- **スレッド別にする理由:** 共有の1ファイルだと、並行作業で唯一の衝突点になるため。
- **`>>` で1行だけ足す理由:** ファイル全体を読んで書き直さないため。
- **`by` で書き手を区別する理由:** ユーザーの指示か AI の推測かで、後から信頼してよい度合いが違うため。
- **途中で毎回書かせない理由:** 追記専用なので、漏れても害が小さく handoff で拾える。

### RULES.md

作業時の共通規則（共通的なハマりどころ、繰り返し指摘されること）。新規成果物を作るときに参照させて、繰り返しの指摘を抑える。

個別のレビュー指摘を受けたときに書き込む場所ではない。書くのはユーザーの指示があるときだけで、人間のゲートで守る。

### shared/

スレッド横断で使える、人間が置く参考資料の置き場。AI は読むだけ。

- **用途別のサブフォルダに入れる理由:** 直下を散らかすと掃除の判断ができないため。
- **RULES.md から指す理由:** kickoff は RULES.md を全文読むので、shared/ 自体を毎回読ませる必要はなく、中身が増えても読み込みコストは増えない。
- **弱点は古くなること。** 置いた時点のスナップショットなので、RULES.md に取得元と取得日を書いて補う。

### work/（スレッド内・スレッド共通）

AI が置く一時的なスクリプトや生成物の置き場。目的ごとにサブフォルダを切る。そのスレッドだけで使うなら `<thread-id>/work/`、複数スレッドで使い回すなら `_ops/work/`。

スレッド内の work/ は、不要になったら消してよい。kickoff では読まないので、次のセッションで必要なものは STATE.jsonl の `refs` か `detail` に場所を書いておく。

### archive/

古いスレッドの退避先。移すのは人間で、AI は判断しない。

## スキルに書かない判断

### AGENTS.md

- 核心だけを置き、詳細はスキルに任せる。会話中に読んだスキル本文は長い会話や圧縮で薄まりやすいが、AGENTS.md（CLAUDE.md）は残りやすい、という見立て（仮説。実測はしていない）。
- 1行・`/` 区切りの規則は、守られないとコマンドが壊れる事故が現場で多発したため、核心としてここにも置いた。
- ターン末に「STATE: 更新済 / 変更なし」を1行出させる案は、毎ターン出て鬱陶しいので見送り。AGENTS.md と sync で足りなければ試す。
- フックで強制する案は、ベンダー差とメンテの重さから避ける。入れるなら「STATE.jsonl が長く更新されていなければリマインド」程度の補助にとどめる。

### kickoff

- 立ち上げ手順で推測を禁じるのは、でっち上げたスレッドIDや `title`、無意味な task は形式としては正しく、後から気づきにくいため。ただし、毎回確認すると煩わしいので、確認するのは推測が入るときだけにする。
- 書式の正は kickoff の「4. STATE.jsonl の書き方」。sync には説明を再掲せず、task の行の例を1行だけ置いている。読み込みを増やさないまま、kickoff の内容が圧縮で薄れたときや、STATE に書き写す task の行が無いときでも正しい書式で書けるようにするため。kickoff の書式を変えたら、sync の例も直す。
- 「5」の行き先表は、禁止ではなく案内。AI が「覚えておきたい」と感じる動機ごとに正規の行き先を用意して、note への流入を減らす狙い。誤りの指摘は REVIEW.md、決定はログ、という分担が前提で、実装系の指摘が REVIEW.md に馴染むかはプロジェクトで確かめる。
- ログと HUMAN を途中で毎回書かせないのは、STATE は漏れると次のセッションが壊れるが、ログは漏れても handoff で拾えるため。必須を STATE だけに絞ったほうが守られやすい。
- スレッドの切り方を RULES.md に書かないのは、kickoff のときにやることが RULES.md にあると、スキルと規則の間で参照が絡むため。プロジェクトごとに kickoff を書き換える前提なので、テンプレートの kickoff には一例を書き込まない。
- jsonl は1行が長くなりがちなので、「100行未満」が行数より文字量で重くなるかもしれない。使って確かめる。

### sync

- 「読み込みなし」ではなく「該当行の grep だけ」。置換には正確な現在の行が要るので、ID で grep して1行 Edit できるよう、キー順と ID を固定している。
- 呼ぶのは人間（または AI が勧める）。自動化はしない。
- 人間が STATE.jsonl を直接編集したと言ったときだけ全文を読み直す。それ以外で全文を読ませると、sync の安さが失われる。
- 引用符は「」を基本にする。bash のエスケープ例はサンドボックスで確かめ済み（ヒアドキュメントと printf の結果が一致し、JSON として読める）。PowerShell の例は実行していないので、実機で確かめる。
- ログの追記はヒアドキュメント（`<<'EOF'`）を勧める。シェルのエスケープが要らず、`'` も気にしなくてよい。`\"` が、`\` を使ってよい唯一の例外。

### handoff

- handoff = sync + 終了処理（次のセッションでやることの決定・note の刈り取り・点検）。sync の手順は重複させず参照にした。
- 刈り取りは「提案 → 番号で承認」で、移行先への書き込みは承認後だけ。RULES.md を人間のゲートで守る方針と同じ考え方。承認なしで終わった handoff は、note が残るだけで壊れない。
- note の上限（5件・各100字）は、セッション中は縛らず、handoff の点検でだけ見る。禁止は守れないので、書いた後に見る。

## 運用上の注意

- **並行してもぶつからないはず。** スレッド固有のファイル（HUMAN / STATE / REVIEW / log）は書き手がそのスレッド内に閉じていて、共有ファイル（RULES.md、shared/）は人間の指示・操作でしか変わらない。
- **`_ops/work/` は例外。** 複数スレッドが書ける唯一の AI 書き込み領域なので、目的ごとのサブフォルダに分け、他のスレッドが作ったフォルダは書き換えない（案）。
- **更新忘れの懸念。** 長い会話や安いモデルだと、STATE.jsonl やログの更新を忘れる。STATE が漏れると次のセッションが壊れるので、途中の必須更新は STATE.jsonl だけに絞り（ログと HUMAN は sync / handoff でまとめて）、核心を AGENTS.md に数行で置き、区切りで `/sync` を呼ぶ。
