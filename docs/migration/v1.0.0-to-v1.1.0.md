# 移行ガイド: v1.0.0 → v1.1.0

v1.0.0 のテンプレートで運用中のワークスペースを、v1.1.0 に移す手順。変わるのはレビュー記録の仕組みと、jsonl の書式を確かめるスクリプトの追加。STATE.jsonl・log.jsonl・HUMAN.md・RULES.md の書式は変わらない（v1.0.0 の書式をスキーマにしただけ）。

変更の理由は [DESIGN.md](../DESIGN.md) の「REVIEW.jsonl と未解決一覧」と、[HISTORY.md](../HISTORY.md) の「2026-11-14: v1.1.0 レビュー記録の再設計」を参照。

## 何が変わるか

| | v1.0.0 | v1.1.0 |
| --- | --- | --- |
| 記録のファイル | `<thread-id>-REVIEW.md`（状態の台帳）と `work/review/review-YYYYMMDD-HHmm.md`（日時付きの詳細。レビューごとに増える） | `<thread-id>-REVIEW.jsonl`（永続記録）と `work/review/<thread-id>-review-pending.md`（未解決一覧）の2つだけ |
| 根拠・経緯 | 詳細ファイルに散らばり、消すと失われる | REVIEW.jsonl の経緯の行に追記で残る |
| 人間が見るもの | 日時付きのレビューファイル | 未解決一覧だけ（原文の引用・指摘内容・修正案・次の対応） |
| 状態 | 未対応 / 保留 / 対応済 | `open` / `doing` / `hold` / `resolved` / `withdrawn` |
| 記録の更新 | 人間が頼む・internal-review を呼ぶ | 状況が変わったら AI が返答の前に更新する |
| レビューの順序 | REVIEW.md と RULES.md を読む前にレビュー | 過去の記録を見ずにレビューしてから照合。RULES.md はそのまま適用 |
| kickoff での読み込み | REVIEW.md は関係しそうなとき | 未解決の指摘の行だけを grep（新しいレビューのときは読まない） |
| 書式の確認 | 無し（AI と人間が目で見る） | `_ops/schema/*.schema.json`（JSON Schema）と `python _ops/schema/check.py`。sync・handoff・internal-review の最後に AI が実行する |

## 1. 差し替える前に

- ワークスペースの `AGENTS.md`（`CLAUDE.md`）、`.agents/skills/`（`.claude/skills/`）、`_ops/threads/` をバックアップする。
- 作業中のセッションは handoff で閉じておく。移行中に記録が書き換わらないようにするため。

## 2. テンプレートを差し替える

| ファイル | 手直ししていない場合 | 手直ししている場合（主に kickoff） |
| --- | --- | --- |
| `.agents/skills/internal-review/SKILL.md` | 差し替える | 手直しした箇所を v1.1.0 に移す（全面的に書き換わっているため） |
| `.agents/skills/kickoff/SKILL.md` | 差し替える | 下の「kickoff の変更点」を手で反映する |
| `.agents/skills/sync/SKILL.md` | 差し替える | 「3. レビュー指摘の記録漏れを埋める」と「5. 書式を確かめる」を足し、報告を「6.」にする。「2.」の段落末尾に、レビュー指摘の決定は REVIEW.jsonl に書く旨の1文を足す |
| `.agents/skills/handoff/SKILL.md` | 差し替える | 「1.」「2.」「4.」に足された行（「4.」の最後のチェック実行を含む）を反映する |
| `AGENTS.md`（`CLAUDE.md`） | 差し替える | 「レビュー指摘も返答の前に記録する」の行を足し、1行規則の対象に REVIEW.jsonl を足す |
| `_ops/schema/`（新規） | フォルダごとコピーする | `waitingOn` や `meta.thread` の書式を変えていれば、スキーマの `enum`・`pattern` も合わせる（README の「プロジェクトに合わせる」） |

`_ops/schema/check.py` には Python 3.8 以上が要る（標準ライブラリだけで動く）。Python が無い環境では、スキルの「チェックを実行する」手順は飛ばされるだけで、運用は v1.1.0 のまま回る。

### 先に v1.0.0 の記録を確かめる

`_ops/schema/` を置いたら、レビュー記録を変換する前に一度実行しておくとよい。STATE.jsonl と log.jsonl は v1.0.0 から書式が変わらないので、ここで出るエラーは v1.0.0 のときからの崩れ（キー順の違い、改行やバックスラッシュの混入など）。

```bash
python _ops/schema/check.py
```

古いスレッドにエラーが多いなら、まず `--no-warn` でエラーだけを見て、AI に直させる（「check.py のエラーを直して」）。

Claude と他のツールを併用していて、スキルを `.agents/skills/` と `.claude/skills/` の両方に置いているなら、両方とも直す。

### kickoff の変更点

- description: `「<thread-id>をやって」` を「スレッドIDを挙げて「〜をやって」」にした（山括弧を外した）。「未解決の指摘」を読む対象に足した。
- 「2. 読む」: 読むものを4つにし、4番目に REVIEW.jsonl の未解決の指摘の行の grep を足した。新しいレビューのときは読まない。`-REVIEW.md` を関係しそうなときに読む、の記述を消した。
- 「5. 作業中に守ること」: 行き先表の REVIEW の行を「…、指摘への回答・修正・確認 → REVIEW.jsonl」に、ログの行を「指摘に関わらない、…」にした。REVIEW.jsonl を返答の前に更新する行を足した。
- 「作成ファイル」: REVIEW.jsonl と未解決一覧は最初の指摘のときに internal-review が作る、に直した。
- 「4. STATE.jsonl の書き方」: 末尾に、機械的な定義は `state.schema.json` で、sync と handoff の最後に check.py で確かめる、の行を足した。
- 「5. 作業中に守ること」: `_ops/schema/` はユーザーの指示があるときだけ書き換える、を足した。

## 3. 既存のレビュー記録を変換する

スレッドごとに、`<thread-id>-REVIEW.md` と `work/review/review-*.md` を `<thread-id>-REVIEW.jsonl` に変換する。REVIEW.md が無いスレッドは何もしなくてよい。

変換は AI に頼むのが楽。v1.1.0 のスキルを置いてからセッションを開き、スレッドごとに次のように頼む。

```text
_ops/threads/<thread-id>/ のレビュー記録を v1.1.0 の形式に移行して。
docs/migration/v1.0.0-to-v1.1.0.md の「3. 既存のレビュー記録を変換する」の対応表に従い、
<thread-id>-REVIEW.md と work/review/review-*.md から <thread-id>-REVIEW.jsonl を作り、
internal-review の 4 で未解決一覧を作って。古いファイルは消さないで。
```

テンプレートのリポジトリ（このガイド）がワークスペースから見えないときは、下の対応表をそのまま貼って頼む。

### 対応表

**指摘の行**（指摘1件につき1行）

| v1.0.0 | v1.1.0 |
| --- | --- |
| `### R-001 <指摘の要約>` | `id`（そのまま）、`title` |
| `## 対象: <成果物のファイル名>` | `target`（ワークスペースからの相対パスにする。節名が分かれば足す） |
| `状態: 未対応` | `"status":"open"` |
| `状態: 保留（理由）` | `"status":"hold"`。理由は `action` に書き、人間・顧客待ちなら `waitingOn` を付ける |
| `状態: 対応済` | `"status":"resolved"`（`action` は省く） |
| `対応`（未解決のとき） | `action` |
| レビューファイルの「該当箇所」 | `refs`（`path:開始行-終了行`。今の位置を確かめて直す） |

**経緯の行**（分かる範囲で。無理に作らない）

| v1.0.0 | v1.1.0 |
| --- | --- |
| `指摘` と、レビューファイルの「指摘内容」 | `"kind":"指摘"`。`refs` にそのときの該当箇所 |
| `指摘元: ユーザー指示（YYYY-MM-DD）` | 指摘の行の `"by":"user"`、`date` にその日付 |
| `指摘元: AIのセルフレビュー（YYYY-MM-DD）` | 指摘の行の `"by":"ai"`、`date` にその日付 |
| レビューファイルの「修正案」 | `"kind":"修正案"`（案ごとに1行） |
| `対応`（直した内容が書いてあるとき） | `"kind":"修正"`。コミットが分かれば `commit` |
| 保留の理由（質問中など） | `"kind":"質問"` |
| レビューファイルの「引用」 | 入れない。必要なら短い抜粋を「」で `"kind":"根拠"` の `text` に |

- `date` は `YYYY-MM-DD HH:mm`。時刻が分からなければ、レビューファイル名の `HHmm` を使い、それも無ければ `00:00` にする。
- 経緯が読み取れない指摘は、指摘の行と「指摘」の行だけでよい。推測で回答や判断の行を作らない。
- 変換したら、`"kind":"判断"`・`"by":"ai"`・`"text":"v1.1.0 への移行で REVIEW.md と review-YYYYMMDD-HHmm.md から変換"` の行を各指摘に1行足しておくと、元のファイルを消した後も出どころが分かる。

### 変換後の確認

- `python _ops/schema/check.py <thread-id>` でエラーが無いことを確かめる。REVIEW.jsonl の書式に加えて、未解決の指摘がすべて一覧に載っているか、一覧の各項目に見出しと原文のコードブロックがあるかも見てくれる。移行で作った指摘の行に経緯の行が無いと警告になるので、上の「判断」の行を足しておくとよい。
- 未解決一覧（`work/review/<thread-id>-review-pending.md`）を開き、v1.0.0 の REVIEW.md で未対応・保留だった指摘がすべて載っているか確かめる。原文の引用が今の成果物と一致しているかも見る。
- 次の ID が既存の最大+1 になるか（ID の欠番はそのままでよい）。
- STATE.jsonl の task の `detail` や `refs` が、`-REVIEW.md` や `work/review/review-*.md` を指していたら、`R-001` などの指摘の ID に書き換える。

## 4. 古いファイルを片付ける

確認が済んだら、`<thread-id>-REVIEW.md` と `work/review/review-*.md` を消すか、`_ops/archive/` に退避する。どちらにするかは人間が決める（AI には消させない）。

## 5. RULES.md を見直す

RULES.md に、v1.0.0 のレビュー記録を前提にした規則（例:「要確認事項はレビュー記録で管理する」「レビューファイルに書き出す」）があれば、REVIEW.jsonl と未解決一覧の役割に合わせて書き直す。テンプレートの RULES.md は空の雛形なので、テンプレート側の変更は無い。

## 6. 試す

1つのスレッドで次を試し、未解決一覧と REVIEW.jsonl が期待どおりに変わるか見る。

1. `/internal-review` でレビューを頼む → 指摘の行と経緯の行が増え、一覧に載る。
2. その指摘に回答・指示する（`/internal-review` を呼ばずに、チャットで伝えるだけ）→ 返答の前に経緯の行が足され、一覧の「次の対応」が変わる。
3. 修正させて確認する → 「修正」「確認」の行が足され、`status` が `resolved` になり、一覧から消える。全件片付いたら「未解決の指摘はありません。」になる。

## 提案を Markdown で手元に適用していた場合

v1.1.0 の元になった改善提案を、Markdown の REVIEW.md（指摘ごとに「対象・指摘元・状態・対応・詳細」）で適用していたなら、同じく 3 の手順で変換できる。違いは次のとおり。

- 状態は `未対応→open`、`対応中→doing`、`保留→hold`、`解決→resolved`、`取り下げ→withdrawn`。
- 「詳細」の子項目は、そのまま経緯の行の `kind` に移す。「該当箇所」は `refs`、「経緯」は中身に応じて回答・判断・修正・確認のどれかに振り分ける。「原文」は入れない（抜粋だけ「根拠」へ）。
- 次回 ID の記録は不要になる（最大+1 を使う）。
- 未解決一覧は `work/review/review-pending.md` から `work/review/<thread-id>-review-pending.md` に名前が変わる。作り直せばよい。
- 該当箇所を絶対パスのリンクにしていたなら、internal-review の 4 の書式をそのように書き換えておく（README の「プロジェクトに合わせる」）。
