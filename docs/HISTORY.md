# Thread Handoff 経緯

2026-11-07 までの検討は、次のノートで行っていた。そちらは更新を止めている。ここで省いた細部（旧版の例など）を確かめたいときだけ見る。

`{秘匿されたパス}/タスクと知見を管理する（Thread Handoff）.md`

## 出発点

Someila の開発で、X で見かけたパターン（当時「フォワードプランニング」と即興で命名）を 2026-09-23 から試したところ、かなりサクサク開発できたので、仕事にも応用したいと考えた。

職場での運用で大きく違ったのは次の2点。

- チケットごとにブランチを切った設計タスクが複数並行する。自然とワークツリーを選ぶことになる。
- 意思決定ログがレビュー記録スキルで残されている。レビュー記録ファイル群（個々の指摘、意思決定、積み残し）とレビュー台帳（共通規則の吸い上げ）があり、レビュー時や成果物の作り始めによく読まれる。

### 旧運用

```
/.../develop/
  main-repo/
  main-repo.worktrees/

/.../.agents/skills/internal-review/

  reviews/
```

- 実は並行に向いていなかった。
- 一箇所に知見が溜まるので、ほとんど同じミスを繰り返さず、繰り返しても見せるだけで説教がいらなかった。

## 2026-10-29: 新運用への改訂

職場でのフィードバックをもとに、マルチタスクができるようフォルダ構成を再編し、名称や定義を一般化した。

- **プロアクティブエージェントの永続メモリを調査**（Dots / Grok Bot / Muse / Duet）: 4社とも「プロフィール、作業ノート、スキル、タスク状態」の層構造で、HUMAN / STATE / log / RULES / スキルに対応しており、足すファイルはほとんどなかった。参考にしたのは、メモリを正の情報源にしない、書き手（人間の指示か AI の推測か）を区別する、古いものを消すルールを持つ、ベンダーロックインを避ける、の4点。
- **並行作業での衝突を検討**: `_ops/` は git の外、チケット別ファイルは書き手が1人、RULES.md は人間の指示でしか書かない、ということで大半は衝突しないと判断した。唯一の衝突点だった共有 `log.jsonl` はスレッド別に分割した。
- **チケット・ワークツリー前提を外してスレッドに抽象化**: `worktrees/` を `threads/` に改名した。ワークツリーを使えないプロジェクトがあるため。複数タスクを1作業でやることもあるので、`tasks/` ではなく `threads/` を選んだ。ブランチ等は任意属性に降格した。
- **ファイル名の接頭辞 `<thread-id>-` は残した**: エディタで複数のファイルを開いたときにタブを区別するため。
- **kickoff / handoff / internal-review をスキル化**: `.github/prompts/` をやめた。AI から信頼・アクセス権を得やすいため。旧運用の `learnings.md` と `reviews/` は REVIEW.md と RULES.md に置き換えた。
- **`_ops/` とスキルをプロジェクト直下に置いた**: PJ間では共有せず、共有したいなら束ねたフォルダの一段上に置く方針（職場では設計プロジェクトを束ねて置き、途中からモックを入れても動いた）。→ 2026-11-01 にワークスペース直下へ変更。
- **`.agents/state/` は見送り**: 標準の規約が見つからず、`.agents/` は共有・コミットする設定類の置き場という慣習がある。頻繁に変わる作業メモとは性質が違うので `_ops/` のままにした。
- **`shared/` を追加**（現場フィードバック）: 位置づけは当初「一時しのぎの先行版の置き場」だったが、リポジトリにはないが手元で重要な資料を置く用途のほうが多いと分かり、使い捨てではないものとして修正した。削除条件は一時しのぎのものだけに書く。
- **`work/` を追加**（ユーザーによる構成の手直し）: スレッド内とスレッド共通の2か所。共通 work/ は「他のスレッドが作ったフォルダは書き換えない」ルールで採用した。
- **RULES.md への昇格は「提案」方式に決定**: REVIEW.md に「昇格候補」の印を付ける案はやめた。AI は普遍的だという確信が高い（目安 70% 以上）指摘を提案し、書くのはユーザーの指示後。70% は AI の確信度としては当てになりにくいので目安にとどめ、実際の判断は基準（固有ではない、似た規則がない、同種の指摘が複数回）で行う。
- **handoff での shared/ 削除条件の確認は見送り**: 用が済んだら人が自分で消すので、AI に確認させる必要はない。
- **REVIEW.md の「指摘元」項目**: Claude が考えたサンプル仕様で、実際のレビュー記録にあったものとは限らない。
- **説明と経緯を分離**: 説明からは経緯を除き、経緯は別にまとめた。

## 2026-11-01: 命名とワークスペース化

- **類似手法の調査**（英語圏中心）: Memory Bank（Cline）/ GSD / Project Continuity / agent-handover / self-improving 系 / ADR に部品が対応する。スレッド概念、書き手分離による衝突回避、`shared/`、人間ゲート付きの RULES.md 昇格を合わせたものは見当たらなかった。既存手法のいいとこ取りで、メインはキックオフ・ハンドオフの仕組み。レビュー記録・ログ・RULES はその部品。
- **名称を「Thread Handoff」に決定**: 候補の Thread Ledger は、台帳が部品側の言葉で、中核のキックオフ・ハンドオフが見えない。フォワードプランニングの流用は、プロジェクト管理の一般用語と被る。
- **トップ階層をワークスペースに変更**（職場での実態）: `.agents/skills/` と `_ops/` は、複数のプロジェクト・ワークツリーを束ねるワークスペースの直下に置く。`_ops/` を git の外に置きたいことと、プロジェクト直下だとワークツリーがワークスペース外になることが理由。
- **エージェントはワークスペースで起動する**と明記した。

## 2026-11-02: 職場での実感による修正

- **ワークツリーで覗き見する利点を明記**: 未マージのブランチを覗いて「空気を読む」ことが、実際の運用で地味に効いている。
- **ブランチにある資料は `shared/` に置かずワークツリーで覗く**: 鮮度を保ちやすいため。RULES.md の例から「他の人のレビュー中ブランチにあるテーブル定義を `shared/` に置く」を削除した。

## 2026-11-07: 更新漏れ対策とテンプレート化

課題は、会話が長くなると AI が STATE / HUMAN / log の更新を忘れること。kickoff は AGENTS.md で強制でき、handoff は人間が明確な終わりの意思で呼ぶが、途中経過が弱い。かといって kickoff を頻繁に呼ぶと、全文を読む分トークン効率が悪い。

- **`sync` を新設**: 途中経過を書くだけの軽量スキル。handoff は「sync + 終了処理」と再定義した。
- **途中の必須更新は STATE だけに絞った**: kickoff の「判断したことはログにすぐ書く」は緩めた。
- **AGENTS.md に更新の鉄則を数行置いた**。
- **STATE.md を STATE.jsonl に構造化**: 見送ったのは次の案。
  - GitHub Issue・カンバン: 書き込み先が変わるだけで更新漏れは解決しない。人間向けの UI やレビュー管理は別の課題。
  - markdown 表・CSV: タスク文の `,` や `|` で壊れる。安いモデルは表の編集で崩す。
  - 追記型: どうせ grep で ID を確かめたがるので、更新型でよい。
- **スキーマの方針**: 自由度は欄の分離で確保する（AI が長大に書く・簡素すぎる、の両方を防ぐ）。旧 STATE.md の「作業中タスク・ブロッキング」「次タスク」「将来タスク」は、`status` と `waitingOn` に分解した。
- **タスク横断の内容を `note` 行に分離**: 旧 STATE.md が汚れていた主因は、タスク・恒久的な知識・決定の同居だった。
- **動機別の行き先表を kickoff に入れた**（禁止ではなく案内）。
- **handoff の刈り取りは「提案 → 番号で承認」にした**。
- **人間が STATE を直接編集する案は主軸にしない**: AI は変更を知らず、結局「読み直して」と伝える必要があり、古い内容で上書きされる恐れもある。sync の後のレビューとしてだけ採用した。
- **dream 系（日次サマリ・自動スキル化）は採用しない**: 公開されている設計説明を調べただけで、実運用での出来は確認できていない。欲しい機能は既にある（同じ指摘の規則化 = internal-review の RULES 昇格提案、日ごとの記録 = log.jsonl）。日次サマリが要るなら、log.jsonl から生成する派生ビューとして必要になったときに作る。
- **スキルを要件の箇条書きから SKILL.md の実例に変更**: 土台は patto-v の実際の SKILL.md で、log の形式もそれに合わせた。
- **STATE.jsonl・ログの値は1行、パスは `/` 区切りをルール化**: 現場でエスケープが原因のコマンド失敗が多発していたため。引用符は「」を基本にし、やむを得ない場合のエスケープ例を sync に入れた。
- **kickoff 冒頭の「（構成は CLAUDE.md）」を削除**: AGENTS.md にツリーを載せない方針なので参照先が無く、必要なパスは kickoff / sync に書いてあるため。
- **ノートの例を実ファイルに移した**: 例では構成が分かりづらく、AI のメタ認知も厳しくなってきたため。本物のワークスペースと見分けがつくよう `workspace/` の下に作り、サンプルの中身は入れずテンプレートにした。kickoff / sync / handoff / AGENTS.md はノートの実例をそのまま切り出し、internal-review の SKILL.md は要件から書き起こした。
- **プロジェクトの置き場の例を `repos/` に**（ユーザー）: テンプレートに `repos/` を追加した。
- **空フォルダに `.gitkeep` を置いた**（ユーザー）。
- **検討資料を `docs/` へ移した**: 陳腐化を防ぐため、ノートの更新を止めてここでメンテする。実ファイルで分かる内容は参照に置き換え、設計の理由と運用メモだけを残した。
- **構造の説明は一か所に集約しない**: 全体をまとめると読む量が増えて、AI が見なくなる恐れがある。危ないのは定義の持ち主が複数いることなので、定義の持ち主を一つに保ち、スキルには作業に必要な分だけを置く。全体の地図は人間向けに DESIGN.md が持つ。`STRUCTURE.md` の新設と、AGENTS.md へのツリー掲載は見送った。
- **kickoff の内容が手元にないときの穴を埋めた**: sync に task の行の例を1行足した（書き写す行が無いと書式を推測することになるため）。sync と handoff に、今のスレッドが分からなければ尋ねる指示を足した（別スレッドへの誤記を防ぐため）。書式の崩れが実際に出たら、説明を増やすより、handoff の点検で STATE.jsonl を機械的に検査するスクリプトを検討する。
- **`meta` に `title` を必須で追加**（ユーザー）: `meta` が紐付けだけだと、スレッド名しか手がかりがなく、何のためのスレッドか分からないため。あわせて、実質同じ内容を書く欄で役割が重なる `tasks` を廃止した（AI の判断）。スレッドの一覧も `meta` の行を grep して `title` つきで見せる。
- **スレッドの立ち上げ手順を、指示が曖昧でも動くように修正**: 新規セッションで「スレッドを立ち上げて」とだけ言われると、材料がないのにスレッドIDと `title` を決めることになり、モデルによってはでっち上げかねなかった（kickoff の記述からの予想で、実機では未確認）。先に RULES.md を読む、目的が分からなければ尋ねる、推測が入るものは確認してから作る、ブランチ等は RULES.md に従う（→ 下の「スレッドの切り方は」で撤回）、具体的な指示が無ければ task を作らない、とした。
- **スレッドの切り方は kickoff を書き換えて定義する**（ユーザー）: kickoff のときにやることを RULES.md に書くのは不自然で、参照が絡んでスパゲッティになるため、RULES.md の見出し「スレッドの切り方」と、それを見に行く kickoff の手順を消した。定型的なプロジェクトでは、kickoff の「新しいスレッドの立ち上げ」を書き換える。命名パターンの表をテンプレートの RULES.md や kickoff に置く案は、一例にすぎないので見送った。
- **使い方を README.md に分離**（ユーザー）: DESIGN.md は設計思想を書く場所なので、導入の手順と人間がやることを分けた。DESIGN.md には理由と判断だけを残す。
- **README の冒頭で、何のためのものかを説明**（ユーザー）: 「ハーネスの上に乗る、コンテキスト・状態管理の運用プロトコル」という説明は、正しいかどうかも微妙で分かりにくかった。困りごととその解決の仕組みから説明する形に書き換え、DESIGN.md の冒頭は README への参照にした。困りごとに、ツールをまたぐと状況を共有できないことを加えた。
- **カスタマイズできる箇所を README の「プロジェクトに合わせる」にまとめた**（ユーザー）: スレッドの切り方、`waitingOn` の語彙、`meta` の属性。あわせて kickoff では `meta` のキーを必須と任意に分けた。
- **スレッドIDのパス区切り文字の注意を kickoff から README へ移した**: テンプレートのままなら、IDは英小文字・数字・ハイフンなので起きない。起きるのはブランチ名をIDにする書き換えをしたときなので、その説明の中に置いた。変換規則までは決めず、注意にとどめた（ユーザー）。
- **Claude と他のツールを併用するならスキルを両方に置く**: `.agents/skills/` を `.claude/skills/` に変えるだけだと、他のツールで `/kickoff` が使えず、ツールをまたいで共有するという目的と矛盾するため。
- **レビュー結果を日時付きのレビューファイルに書き出す**（ユーザー）: 現場で使うと指摘文が簡素で、箇所の指定もまちまちだったため。`work/review/` に、該当箇所（ワークスペースからの相対パス:行番号と引用。フルパスは bash と pwsh でドライブレター付近の書き方が変わるうえ、相対パスなら VS Code のパレットで開ける）・指摘内容・修正案の書式で書き出す。REVIEW.md は状態の台帳として残し、番号を共通にしてレビューファイルを指す（AI の判断。再発の確認と RULES.md への昇格に使うため）。
- **STATE.jsonl と RULES.md は基本 AI が書くと README に明記**（ユーザー）: 人間が触ってもよいが、主に書くのは AI だと分かるようにした。
- **単純なコミット・プッシュ・マージはログに書かない**（ユーザー）: 現場で、単純なコミットの実施までログに書かれてノイズになっていたため。
- **kickoff でチャットセッションのタイトルを `<title>:<指示内容>(<thread-id>)` に変更する**（ユーザー）: 自動生成のタイトルに CLAUDE.md は効かないという報告があり（公式の仕様は未確認）、スレッドが決まる kickoff で付けるほうが確実なため。変更ツールがある環境だけで行う。Codex で、頼めばタイトル変更ツールで変更できることはユーザーが確認した。kickoff の記述で実際に動くかは未確認。
