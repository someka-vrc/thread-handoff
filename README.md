# Thread Handoff

AI エージェントとの作業を、セッションが変わっても続きから再開できるようにする、フォルダ構成とスキルのテンプレートを提供する。

## 目的

AI との作業には、次の困りごとがあった:

- 会話が長くなったりセッションを変えたりすると、状況や決めたことが失われる
- 複数の作業を並行すると、状況が混ざる
- セッションを変えると、過去に指摘した間違いをAIが繰返してしまう
- エージェントツールをまたぐと状況を共有できない

そこで、作業を「スレッド」という単位に分け、やること・決めたこと・レビューの指摘をスレッドごとにファイルで残す仕組みを構築する。
AI は `/kickoff` で作業を始め、`/handoff` で次のセッションへ引き継ぐ。繰り返し指摘されることは、人間の承認を経て共通規則として覚える。

使用するファイルは Markdown と JSONL だけで、専用のツールは不要。

## 参照資料

- [docs/DESIGN.md](docs/DESIGN.md): 設計思想と運用方針
- [docs/HISTORY.md](docs/HISTORY.md): 設計の経緯

## 使い方

### 導入

1. `workspace/` を任意の場所にコピーする（ワークスペースと呼ぶ）。
2. プロジェクトを `repos/` に置く。設計・モック・実装プロジェクトやそのワークツリー、ナレッジ、ノウハウ、顧客授受資料など、何でも入れてしまうとよい。
3. Claude を使うなら `AGENTS.md` を `CLAUDE.md` に、`.agents/skills/` を `.claude/skills/` にする。Claude 以外と併用するなら両方に置く。
4. 必要ならプロジェクトに合わせて書き換える（下の「プロジェクトに合わせる」）。
5. エージェントをワークスペースで起動する。

### プロジェクトに合わせる

- `.agents/skills/kickoff/SKILL.md`
  - **スレッドの切り方:** スレッドの切り方が定型的なら、「新しいスレッドの立ち上げ」を書き換える（ブランチ名の提示を必須としてスレッドIDに使用するなど。スラッシュを含むブランチ名に注意）。スレッド作成と同時に同名の追加ワークツリーが存在しなければ作成(git worktree add)するように指示するのも良い。
  - **`waitingOn`(待ち理由) の語彙:** kickoff の「4. STATE.jsonl の書き方」でカスタムする。 初期定義は `human`(ユーザー) / `client`(顧客)。
  - **`meta` の属性:** スレッドに紐づける情報(チケットやブランチ、ワークツリーフォルダなど)を属性として定義する。
  - **セッションタイトルの自動カスタム:** スレッドの開始時にセッションタイトルを自動編集させるには、「1. スレッドを決める」でタイトル書式を指定する。自動編集させないなら行ごと消すこと。

### 作業の流れ

| いつ                                   | 呼ぶもの               | 人間がやること                                                          |
| -------------------------------------- | ---------------------- | ----------------------------------------------------------------------- |
| 始めるとき・別セッションで再開するとき | `/kickoff <thread-id>` | 新しいスレッドなら、何のためのスレッドかを伝える                        |
| 区切り                                 | `/sync`                | STATE.jsonl をざっと見て直す（AI の更新漏れや解釈ズレのレビューになる） |
| 終えるとき・話題が変わるとき           | `/handoff`             | note の処置案を番号で承認し、STATE.jsonl をざっと見て直す               |
| レビューしてほしいとき                 | `/internal-review`     | `work/review/` のレビューファイルを読み、対応を決める                   |
| 誤りを指摘するとき                     | `/internal-review`     | 普遍的な指摘を提案されたら、RULES.md に入れるか決める                   |

### 人間が手で触るもの

#### HUMAN.md

AI が書いた、人間にしかできないことのチェックリスト。済んだら行ごと消してよい。

#### STATE.jsonl

基本は AI が更新する。手で直してもよいが、直したら AI に「STATE を読み直して」と伝える。AI は変更を知らず、古い内容で上書きしかねない。

#### RULES.md

基本は AI に指示して書かせる（例: 「R-001 を RULES に入れて」）。AI が自分の判断で書き込むことはない。手で直してもよい。ドキュメント種類やセクションで階層化して、ある程度見やすくする。

育った状態の例（架空）:

```markdown
## 共通

- 項目の桁数・型は項目定義書を正とする。設計書側で独自に書かない
- クライアントへの質問中の事項は、設計書に「未確定」と明記してから先へ進む

## 参照優先（_ops/shared/）

- プログラムIDは `_ops/shared/program-ids/プログラムID一覧.csv` を参照する。リポジトリにはない
  - 取得元: Teams の「◯◯」チャネルのファイル、取得日: 2026-10-29
  - 更新: Teams 側が更新されたら取り直す

## 画面設計書

### 入力項目

- 必須・任意、桁数、デフォルト値を全項目に記載する
- 検索条件は初期表示時の絞り込み状態も記載する
```

#### shared/

AI に参照してほしいが、git の変更には載せたくないファイルを置く。

- **置くもの:**
  - リポジトリにはないが、手元で重要な参考資料（例: Teams にあるプログラムID一覧を CSV にしたもの）。本来リポジトリに置くべきレベルのもので、この用途が一番多い。
  - どこにも書かれていないし書いてはいけない不文律を文書化して、AI に知らせるもの。
- **置き方:** 用途別のサブフォルダに入れ、RULES.md に「◯◯は shared/xxx を優先して参照する」と書く（上の例を参照）。
- **古くならないように:** RULES.md に取得元と取得日を書く。恒久的な資料は、元が更新されたら取り直す。一時しのぎのものだけ削除条件（例: main に入ったら外す）も書く。
- **不要になったら:** 削除するか `archive/` へ退避する。
- **置かないもの:** ブランチに乗っている資料。ワークツリーで見たほうが鮮度を保ちやすい。

#### archive/

PR がマージされ、吸い上げも済んだ古いスレッドは、手で `_ops/archive/threads/` へ移す。スレッド内の work/ も一緒に移す。
